## Context

The ADB Logstream viewer is an Angular 21+ client that renders log entries streamed via WebSocket. State is managed via signals in `LogStateService`. Each `LogRowComponent` currently manages a local `selected` signal that is not accessible to other components (header, footer). The `LogstreamEntry` model includes a `uuid` field generated by the server, designed for future extensibility including selection.

The header contains brand/status, search bar, level toggles, entry count, and a Clear button. The footer contains keyboard shortcut hints and an auto-scroll toggle.

## Goals / Non-Goals

**Goals:**

- Centralize selection state in `LogStateService` so header, footer, and log rows all share the same selection
- Replace per-row local `selected` signal with service-driven selection
- Show a Copy button in header and footer conditionally (when selection is non-empty)
- Copy selected entries as a formatted JSON array to the clipboard
- Clear selection and show "Copied!" feedback after successful copy
- Handle clipboard API errors gracefully

**Non-Goals:**

- Select All / Deselect All buttons
- Shift+click range selection
- Keyboard shortcut for copy (could be added later)
- Export to file (only clipboard)
- Persisting selection across page reloads
- Server-side changes

## Decisions

### 1. Centralize selection in `LogStateService` as `signal<Set<string>>`

- **Why**: Header and footer need to react to selection changes (show/hide Copy button). Per-row local state cannot communicate upward. A `Set<string>` keyed by UUID is O(1) for add/remove/check and naturally deduplicates.
- **Alternative considered**: Array of UUIDs — rejected because add/remove/has are O(n) and duplicates require extra logic.
- **Alternative considered**: `signal<Record<string, boolean>>` — works but `Set` is more idiomatic for a collection of unique IDs.

### 2. `LogRowComponent` reads selection from service instead of local signal

- **Why**: The checkbox checked state must reflect the centralized selection. The component already receives `entry` as an input, so it can check `logState.isSelected(entry.uuid)`.
- **Implementation**: Remove local `selected` signal. Add a computed `isSelected` in the component or call `logState.isSelected(uuid)` directly. The `toggleSelected()` method calls `logState.toggleSelection(uuid)`.

### 3. Copy button appears via `@if` based on computed `hasSelection`

- **Why**: Conditional rendering with Angular's new control flow is clean and avoids hidden/disabled button complexity.
- **Implementation**: `hasSelection = computed(() => this.logState.selectedUuids().size > 0)` in header and footer components. Template: `@if (hasSelection()) { <button>Copy</button> }`.

### 4. Use `navigator.clipboard.writeText()` for clipboard access

- **Why**: Native browser API, no dependencies needed. Well-supported in modern browsers.
- **Risk**: Clipboard API requires secure context (HTTPS or localhost). Dev server runs on localhost, so this is fine. Production use behind HTTPS also fine.

### 5. Post-copy: clear selection + brief "Copied!" toast

- **Why**: Users expect confirmation after copy. Clearing selection signals the action completed. A simple CSS-animated toast or a temporary text change on the button is sufficient.
- **Implementation**: After successful `writeText()`, call `logState.clearSelection()` and show a "Copied!" message that fades out after ~2 seconds.

### 6. JSON format: `JSON.stringify(selectedEntries, null, 2)`

- **Why**: Formatted JSON is human-readable and easy to paste into tools, editors, or share. The 2-space indent is consistent with common conventions.

## Risks / Trade-offs

- **[Risk]** `navigator.clipboard` unavailable in non-secure contexts or older browsers → **Mitigation**: Feature degrades gracefully — button can be hidden or show an error message. In practice, the app runs on localhost (dev) or behind HTTPS (prod).
- **[Risk]** Large selection (hundreds of entries) could produce a very large clipboard payload → **Mitigation**: Not a practical concern for a log viewer; the 5000-entry cap limits worst case.
- **[Risk]** Selection state is lost on page reload → **Mitigation**: Acceptable for this use case. Persisting selection would add complexity with no clear user benefit.

## Migration Plan

No migration needed. This is a purely additive client-side feature. The only change to existing code is replacing the local `selected` signal in `LogRowComponent` with service-driven selection, which is a refactor with no behavior change for the checkbox UI itself.
